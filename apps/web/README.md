# Фронтенд канваса (`@canvas/web`)

Редактор рабочего пространства на React 19 + TypeScript + React Flow (`@xyflow/react`). Три типа нод — **текст → генератор → результат** — соединяются перетаскиванием, граф сохраняется на бэкенд с debounce 500 мс, генерация изображения имитируется сервером и отслеживается опросом.

[Задание](../../docs/ASSIGNMENT.md) · [API](../../docs/INTEGRATION.md) · [Критерии оценки](../../docs/EVALUATION.md)

## Запуск

Нужен поднятый бэкенд (см. корневой [README.md](../../README.md)). После `npm ci` в корне репозитория:

```sh
npm run build -w @canvas/contracts   # один раз — контракты нужны как workspace-зависимость
npm run dev -w @canvas/api           # терминал 1: бэкенд на 127.0.0.1:4001
npm run dev -w @canvas/web           # терминал 2: фронтенд (Vite)
```

Сборка и предпросмотр собранного бандла:

```sh
npm run build -w @canvas/web
npm run preview -w @canvas/web
```

Адрес API задаётся переменной окружения `VITE_API_BASE_URL` (по умолчанию `http://127.0.0.1:4001`); фронтенд может работать на любом порту `localhost`/`127.0.0.1`, как и допускает бэкенд.

## Проверенные сценарии

- Создание пространства и его повторное открытие после перезагрузки страницы (id пространства хранится в URL, `?space=...`).
- Добавление всех трёх типов нод, редактирование текста промпта.
- Соединение прометром→генератор→результат перетаскиванием; запрет некорректных связей (не тот тип, второй вход на занятом порте, второй выход у генератора), лимиты 20 нод / 20 связей.
- Debounce-сохранение: серия быстрых правок даёт один `PUT` после паузы, одиночная правка тоже сохраняется; статус-бейдж отражает «Сохранение…/Сохранено/Есть несохранённые правки/Ошибка».
- Клик «Сгенерировать» сразу после правки: несохранённое состояние флашится до старта генерации, генерация стартует с получившимся ETag.
- Сценарии генерации «успех» и «отказ» через явный переключатель у генератора; повтор после отказа — новым `Idempotency-Key`.
- Восстановление графа и истории генераций после перезагрузки, включая продолжение опроса незавершённой генерации.
- Конфликт версии графа (412): локальный черновик не теряется, показывается баннер с явной кнопкой «Перечитать граф с сервера» — без автоматического повтора и без молчаливого затирания.
- Каскадное удаление ноды вместе со связями (кнопка Delete/Backspace на канвасе).

## Известные ограничения

- Если нода-результат удаляется после того, как генератор получил статус (успех/отказ), бейдж генератора не сбрасывается в «Не запущено» до следующего запуска — сама генерация корректно перестаёт отображаться (рендерить её больше некуда), но статус на генераторе визуально «зависает».
- Автоматических фронтенд-тестов нет — только ручная проверка сценариев выше (описано в [docs/EVALUATION.md](../../docs/EVALUATION.md): количество тестов не даёт преимущества, важнее подтверждённое поведение).
- Опрос генерации использует фиксированный интервал из `GET /api/config` (`pollIntervalMs`), а не заголовок `Retry-After` конкретного ответа — сервер всё равно возвращает в нём константу, отдельная логика ради этого не оправдана.

## Как устроена работа с API

Все запросы идут через `src/lib/api/client.ts` — единственное место, где вызывается `fetch`. `apiRequest()` строит URL и заголовки, различает 204/304 (без тела), парсит JSON, а любую сетевую/HTTP/парсинг-ошибку приводит к одному виду — `ApiError { code, message, status }`. Компоненты никогда не видят `Response` и не пишут свой `try/catch` вокруг `fetch`: они получают либо готовые данные, либо уже разобранную `ApiError`. Поверх лежат тонкие типизированные обёртки (`spaces.ts`, `graph.ts`, `generations.ts`, `config.ts`), каждая из которых лишь описывает свой путь/метод/заголовки.

### Debounce и очередь сохранений

`GraphSyncController` (`src/features/graph/GraphSyncController.ts`) — единственное место, откуда уходит `PUT` графа. Локальные правки (перетаскивание, ввод текста, добавление/удаление нод и связей) применяются к состоянию сразу и планируют сохранение через debounce (500 мс из `GET /api/config`). Метод `ensureSaved()` — единственная точка входа для отправки: если `PUT` уже выполняется, конкурирующий вызов дожидается его и на каждой итерации заново проверяет, не появились ли новые правки, — поэтому одновременно никогда не летит больше одного `PUT`, а более новое локальное состояние не может быть затёрто ответом на более старый запрос. `flush()` (используется перед стартом генерации) — это тот же `ensureSaved()`, вызванный сразу, без ожидания таймера debounce.

При `412 GRAPH_VERSION_CONFLICT` черновик не отбрасывается и повтор не запускается автоматически — выставляется явный флаг конфликта, который снимается только явным действием пользователя (перечитать граф). Если ответ на `PUT` теряется (сетевая ошибка), контроллер перечитывает граф и сравнивает его **байты** с тем, что было отправлено: совпадение означает, что запись всё же прошла и ответ просто потерялся (ETag принимается, ничего не отправляется повторно); несовпадающий ETag относительно того, что было `If-Match`, означает реальный конкурентный конфликт — он обрабатывается так же, как обычный 412, а не ретраится вслепую (иначе можно было бы молча затереть чужую правку).

### ETag

ETag графа — строгий, привязан только к ресурсу графа и никогда не вычисляется на клиенте: используется ровно то значение, которое последний раз вернул сервер (из `GET` или предыдущего `PUT`).

### Идемпотентность и опрос генерации

`useGenerations` перед стартом всегда флашит сохранение и берёт `graphETag` из подтверждённого `committedEtag`, затем шлёт `POST` с новым `Idempotency-Key` — это всегда новая попытка. Retry после сетевой ошибки самого `POST` (ответ не пришёл) переиспользует тот же ключ и то же тело — сервер по ним же (`nodeId`, `graphETag`, `scenario`) распознаёт, что это тот же запрос. Опрос статуса (`GET .../generations/{id}`) идёт через общую `pollUntilSettled()` (`src/lib/async/poll.ts`) с отменой через `AbortController`, который останавливается при закрытии пространства/размонтировании. После перезагрузки список генераций (уже отсортирован сервером от новых к старым) сводится в `Map` одним проходом (`pickCurrentGenerations`, `src/lib/generation/reconcile.ts`): для каждой пары генератор/результат берётся только первая (то есть самая свежая) запись, более старые и записи с удалёнными с тех пор нодами отбрасываются — так более новый запуск или рассоединённая цепочка никогда не подставит устаревшую картинку в чужую или более новую ноду.

## Производительность: `toPersistedGraph`

`src/lib/graph/persist.ts` — функция на пути каждого сохранения графа: она вызывается один раз на каждый подтверждённый `PUT` (не на каждое нажатие клавиши — debounce уже схлопнул промежуточные правки к этому моменту), и переводит рабочие объекты React Flow (несущие служебные поля `selected`, `dragging`, `measured`, обработчики событий) в JSON-схему, которую принимает сервер.

- **Частота вызова**: ровно один раз перед каждым фактическим `PUT` — не на каждый рендер и не на каждое изменение курсора.
- **Число проходов**: один `.map()` по `nodes` и один `.map()` по `edges` — итого два линейных прохода суммарной длины `nodes.length + edges.length` (≤ 40 элементов при лимитах API), без вложенных проверок и без повторного поиска по `id` (узлы и связи независимы, перекрёстных сопоставлений тут не требуется).
- **Выделение памяти**: создаются ровно те объекты, что уйдут в тело запроса, — никаких промежуточных отфильтрованных/скопированных массивов (`.filter().map()` и подобных цепочек тут нет, только один проход на каждый массив).

Аналогичным принципом (индекс строится один раз через `useMemo` и переиспользуется, а не пересчитывается на каждое движение мыши) построена проверка допустимости соединений: `buildDegreeIndex` (`src/lib/graph/rules.ts`) один раз на изменение `edges` строит две `Map` (вход по цели, выход у генератора), и `isValidConnection` во время перетаскивания делает по ним `O(1)`-подстановку вместо линейного поиска по массиву связей на каждый кадр перетаскивания.
